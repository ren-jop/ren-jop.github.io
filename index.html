Engineering approach

I prefer systems that remain understandable at failure boundaries: when state changes, a process exits, hardware behaves differently than expected, or an integration stops agreeing with its assumptions.

Give state one owner

A timer, schedule or policy should have one authoritative owner. Integrations pass context instead of creating parallel truth.

Prefer observable behaviour

Compiler output, runtime state, logs, measurements and hardware documentation outrank assumptions about how a system should behave.

Make operation boring

Install, update, diagnostics and recovery are part of the design. A project is easier to trust when its operational path is explicit.

Ship the smallest coherent loop

Validate a complete build → run → interact → inspect path early, then widen the system without losing the working baseline.

Across the stack

I gravitate toward work that crosses boundaries: GUI to daemon, calendar to timer, firmware to PCB, and procedural generation to player feedback.
